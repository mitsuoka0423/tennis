**状態: W0 進行中**（2026-07-25 作成 / T1 完了）
**仕様**: [docs/RECORDING_RELIABILITY_SPEC.md](../RECORDING_RELIABILITY_SPEC.md)
**契機**: 2026-07-21 実機検証で 325スイング中クリップ1件のみ生成される不具合を確認

---

## 方針

原因は「自動ロックで録画が止まり、再開経路が無い」ことだが、
**特定の中断要因だけを塞ぐのではなく、中断一般から復帰できる構造にする**。

理由は2つ。

1. 今回の中断要因は「自動ロックである」と断定できていない。ログが1行も残っておらず、
   ファイル配置からの逆算で「開始4〜29秒後に停止」までしか絞れていない。
2. カメラ撮影を継続できるバックグラウンドモードは iOS に無いため、
   着信等による中断はどのみち発生する。防ぐのではなく復帰させる必要がある。

あわせて **W0（観測性）を最初に片付ける**。実機検証は1時間の実練習が必要で再現コストが高く、
次の検証を無駄にしないため。

### W5: 検出閾値の再評価（独立）

- [x] **T11: 保全データでの閾値分析** ✅ 2026-07-25（分析のみ。実装変更は保留）
  - 対象: 2026-07-21 セッションの 325件（下記「保全データ」参照）
  - 成果物: `~/Documents/TennisAnalyser-FieldData/2026-07-21/threshold_analysis.{py,md}`
  - **結論: 閾値 3.0g は据え置き。上げる根拠が得られなかった**

  前提が2つ誤っていた。

  1. `Swing.peakAcceleration` は**トリガ値ではなく4秒窓全体の最大値**
     （`samples.map(\.accelerationMagnitude).max()`）。実際のトリガ値は中央値 3.41g。
     窓が隣接スイングのピークを拾うため、ピークが Impact から 200ms 超ずれる窓が 116件（35.7%）
  2. 4.0g へ上げたときの脱落は「49件（15.1%）」ではなく **99件（30.5%）**（Impact±150ms で判定）

  低g帯（3〜4g）は誤検知ではない。波形は鈍い（立ち上がり 224 vs 710 g/s）が、
  ジャイロピーク中央値 525 deg/s はラケット回転として十分大きく、
  **加速度あたりの回転はむしろ低g帯が1.48倍大きい**（非スイング動作なら逆になる）。
  「弱い・回転が乏しい・鈍い」を全て満たすのは 13件（4.0%）のみ。

  | 閾値 | 残存（Impact±150ms 判定） |
  |---:|---:|
  | 3.0g | 325 (100%) |
  | 4.0g | 226 (69.5%) |
  | 5.0g | 173 (53.2%) |
  | 6.0g | 135 (41.5%) |

  絞るなら閾値ではなく **3.0g + ジャイロゲート**（Impact±100ms で 300 deg/s 以上）が筋が良い。
  除去25件で済み、8g以上の帯域は除外0件＝本物の強打を傷つけない。

  > **ラベルが全件空欄**（328ファイル・約26万行すべて）のため precision/recall は算出不能。
  > 上記はすべて分布の質的比較にとどまる。閾値を**下げた**場合の増加件数も、
  > 3g未満のセンサー値が保存されていないため算出できない。
  > 付随: 43窓で加速度計が飽和（±15.9g到達）しており 12g超の絶対値は不正確な可能性。

- [ ] **T12: re-arm の見直し（T11 で発見。閾値より優先度が高い）**

## 再開手順

1. 本ファイルのチェックボックスで進捗を確認する
2. `git log --oneline -10` で直近のコミットを確認する
3. `Logs/{最新日付}.log` のネクストアクションを読む
4. ビルド確認（iOS/Watch 両方。AGENTS.md ルール5）
5. 未完了の最初のタスクから着手する

Wave の途中で中断した場合は、そのWaveの完了済みタスクまででビルドが通る状態に
してからコミットすること（AGENTS.md 方針1）。

### コンテキスト運用ルール

1セッションのコンテキストは 200k。**状態を知るための操作**が最も高くつくため、以下を守る。

| ルール | 理由 |
|---|---|
| `git diff` は必ずパス指定（`git diff -- <file>`） | パス無しの全体 diff は単発で約 8k を消費する |
| 200行超のファイルは全読みしない。`grep -n` で当たりを付けて `Read` の offset/limit | 3ファイル全読みで約 7k |
| ビルド出力は捨てる: `xcodebuild ... 2>&1 \| tail -8` | 成功時の全ログは無価値 |
| 本ファイルは該当 Wave だけ読む | 全文 180行超 |
| **Wave 完了ごとにコミットし、チェックボックスを更新する** | 未コミット状態は次セッションに全体 diff を強制する |

### サブエージェントへの委譲

委譲コスト（ブリーフィング＋報告受領）は 3〜5k。**中間生成が 10k を超えるタスクのみ**委譲する。

| 委譲する | 理由 |
|---|---|
| W5 の閾値分析 | Swift 不要・リポジトリ非依存。中間生成 15〜25k |
| 変更前の影響範囲調査（Explore） | fan-out 検索は中間が大きく結論は小さい。規約のブリーフィング不要で委譲コストが 1k 以下 |
| 実機ログ（logarchive）からの事象抽出 | 生ログは大量、結論は数行 |

| 委譲しない | 理由 |
|---|---|
| 実装そのもの | diff レビューが必須で、読むコスト ≒ 書くコスト。規約（コメント How/What/Why not・正式名称）の伝達分だけ純損 |
| ビルド確認・コミット・doc 更新 | `\| tail` 済みで数百トークン。冷えた起動の方が高い |
| Wave 間の設計判断 | 文脈が必要。冷えた状態の判断は品質リスク |

> 例外: Wave の途中でコンテキストが逼迫した場合は、残りを詳細スペック付きで委譲し
> 自分はレビューに専念する。窓を使い切って巻き戻すよりは確実に安い。
