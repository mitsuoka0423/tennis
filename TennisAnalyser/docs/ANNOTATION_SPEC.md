## 1. 目的

連続記録した動画とセンサー時系列に対し、練習後にスイングの位置と球種をタグ付けする。
出力は Create ML の学習データとなる。

---

## 2. 支配的な制約はスループット

2026-07-21 の実測で **1時間の練習に約325スイング**。ここから逆算する。

| 1件あたり | 325件の所要時間 |
|---:|---:|
| 5秒 | 27分 |
| 10秒 | 54分 |
| 15秒 | 81分 |

**練習1時間に対しタグ付けが1時間かかる設計では運用が破綻する。**
本仕様は「1件あたり5秒以下」を設計目標とし、以下の全ての判断をこれに従属させる。

---

## 3. 中心となる設計判断

### 3.1 動画を走査させない。候補を提示して選別させる

ユーザーが1時間の動画をスクラブして打点を探す設計にはしない。
オフライン検知器（W6-T15）が候補を提示し、ユーザーは**選別だけを行う**。

> Why not 全編スクラブ: 1時間の動画から325箇所を人が探すのは、
> 探索そのものにタグ付け以上の時間を要する。検知器は 3.0g 閾値で
> 実用上ほぼ全ての打球を拾えている（2026-07-21 の分析で確認）。

### 3.2 検知器の見落としは波形で発見させる

検知器が拾えなかった打球は、**センサー波形上で「マーカーの無いピーク」として視認できる**。
動画を見なくても、波形をスクロールするだけで見落としを発見できること。

> 2026-07-21 の分析では re-arm により 3g超イベントの42%が未発行だった。
> 連続記録では検知器のパラメータを事後に変更できるため見落とし自体が減るが、
> ゼロにはならない。人が補完する経路を必ず用意する。

### 3.3 却下は削除しない

「スイングではない」と判断した候補は、**却下として記録し保持する**。

> Why not 削除: 却下は「検知器がここで誤って発火した」という負例であり、
> 検知器を改善するための情報を持つ。削除するとその情報が失われ、
> 同じ誤検知を何度も却下し直すことになる。

### 3.4 中断・再開できること

325件の選別を一度に終える前提を置かない。1件ごとに永続化し、
どこまで見たかを保持して再開できること。

## 4. データモデル

```
SessionAnnotation {
    sessionId: String
    events: [AnnotatedEvent]
    timeOffsetSeconds: Double     // 5.3 の全体補正
    updatedAt: Date
}

AnnotatedEvent {
    id: String                    // UUID
    impactAt: Date                // 壁時計。動画・センサー双方への対応付けの基準
    shotClass: ShotClass?         // nil = 未分類
    status: AnnotationStatus
    origin: EventOrigin
    detectorPeak: Double?         // 検知器由来の参考値（g）
}

enum AnnotationStatus {
    case proposed     // 検知器が提示。未レビュー
    case confirmed    // ユーザーが承認（shotClass 必須）
    case rejected     // ユーザーが「スイングではない」と判断
}

enum EventOrigin {
    case detector     // オフライン検知器が提示
    case manual       // ユーザーが波形上で追加
}
```

`ShotClass` は既存の定義（`SwingRecord.swift`）をそのまま用いる。

```
strokeForehand / strokeBackhand / volleyForehand / volleyBackhand / serve / other
```

保存先: `Documents/annotations/{sessionId}.json`

> Why not スイングCSVへ直接書き込む（現行の `SwingCSVParser.writeShotClass`）:
> 連続記録ではスイング単位のCSVが存在しない。アノテーションはセンサー本体とは
> 独立した薄い層として持ち、切り出しは書き出し時に行う（7章）。
> これにより窓長やラベルを何度でも変更できる。

## 5. 機能要件

### F-I8-1 候補の提示（必須）

* オフライン検知器の結果を `proposed` として一覧・順送りできること。
* 各候補について、動画とセンサー波形を **F-I8-4 と同じ双方向同期**で表示すること。
  * 候補へ移動した時点で `impactAt` の前後を**自動再生**すること（操作不要）。
  * 必要に応じてスクラブでき、その間も波形と動画が同期すること。
  * 波形にはインパクト位置をマーカー表示すること。
  * 検知器のピーク値を表示すること。
* 未レビュー件数と進捗（レビュー済み / 全体）を常時表示すること。

  > Why not スクラブ前提にする: 2章のスループット目標により、大半の候補は
  > 一目で判別できる必要がある。共通経路は**操作ゼロ**で判断できること。
  > 同期スクラブは判断に迷う候補のための手段であり、既定の操作ではない。

  > Why not 静止画やサムネイルで済ませる: 球種の判別には打点前後の動きが要る。
  > また波形のピークと動画の打点がずれている場合、静止画では検知できない。

### F-I8-2 選別と分類（必須）

* **1操作で「承認＋球種指定」を完了できること。** 承認と分類を2段階に分けないこと。
* 却下も1操作で行えること。
* 判断を保留して次へ送れること（`proposed` のまま維持）。
* 直前の操作を取り消せること。

  > 設計目標である1件5秒以下は、この「1タップ完了」を前提として成立する。
  > 球種は6種のため、6ボタン＋却下の計7つを常時表示できる。

### F-I8-3 一括タグ付け（必須）

* 連続する複数の候補へ同一の球種を一括で付与できること。
* 適用範囲を件数または時間範囲で指定できること。

  > 練習はブロック単位で行われることが多い（フォア20本 → バック20本）。
  > 既存の `ContentView.applyBulkTag` が同じ発想で実装済みであり、それを踏襲する。

### F-I8-4 波形と動画の同期再生（必須）

**選別画面・タイムライン画面の双方で用いる共通の仕組みとする。**
両画面の違いは対象範囲だけであり（選別＝候補の前後数秒 / タイムライン＝セッション全体）、
同期の挙動は同一とすること。

* 波形と動画を**双方向に同期**させること。
  * 波形をスクラブすると、その時刻の動画が追従すること。
  * 動画を再生すると、波形の再生位置が追従すること。
* セッション全体を**1本の連続した時間軸**として扱うこと。
  複数セグメントにまたがっていても、ユーザーからは連続して見えること。
* セグメント境界をまたいでシーク・再生できること。
* セグメント間の欠落（中断区間）を時間軸上に**明示すること**。
  動画が存在しない区間であると判別できること。

  > Why not クリップ単位の同期再生に留める（既存 `VideoSyncPlayerView` のまま）:
  > 見落としの発見は「候補が無い箇所」を見る作業だが、クリップは候補が有る箇所にしか
  > 存在しない。見落としを探すには連続した時間軸の上で動画を確認できる必要がある。

  > 中断区間の明示が要るのは、そこに落ちたスイングが原理的にクリップ化できないため
  > （F-I7-3）。「動画が無い」のか「打っていない」のかを区別できないと、
  > 見落としを探す作業が成立しない。

### F-I8-5 見落としの補完（必須）

* センサー波形をスクロールし、マーカーの無いピークを確認できること。
* 波形上の任意の位置に `manual` イベントを追加できること。
* 追加位置の妥当性を、F-I8-4 の同期再生でその場で確認できること。

### F-I8-6 インパクト位置の微調整（必須）

* 個別イベントの `impactAt` を前後に調整できること。
* 調整の粒度はセンサーのサンプル間隔（5ms）以上、動画フレーム以下の精度を持つこと。

  > 検知器は閾値を超えた**最初のサンプル**を採るため、真のインパクトより
  > わずかに早い。学習データの窓位置に影響するため補正手段を設ける。

### F-I8-7 時刻の全体補正（必須）

* セッション単位で動画とセンサーの時刻オフセットを調整できること。
* 調整結果を `timeOffsetSeconds` として保持し、全イベントへ一律に適用すること。

  > 2026-07-21 の実測では Watch↔iPhone の時計ずれは 56.7分で 0.2秒であり、
  > 前後2秒の窓に対しては十分小さい。ただしずれが常に小さい保証は無く、
  > 個別イベントを1件ずつ直すのは 2章のスループット目標に反するため、
  > セッション全体を一度に補正する手段を設ける。

### F-I8-8 永続化と再開（必須）

* 操作のたびに永続化すること。アプリが終了しても失われないこと。
* 次回起動時、最後にレビューした位置から再開できること。

### F-I8-9 書き出し（必須）

* `confirmed` のイベントのみを Create ML 向けに書き出せること。
* 書き出し時に、連続センサー記録から `impactAt` を中心とする窓を切り出すこと。
* **窓長を書き出し時に指定できること**（既定は前2秒・後2秒）。

  > これが連続記録方式の主要な利点である。窓長を変えて学習し直す際に、
  > 再収集も再タグ付けも不要になる。
* 出力形式は既存の `TrainingDataExporter` を踏襲する
  （`<ShotClass>/<sessionId>_<index>.csv` + `manifest.csv`）。

### F-I8-10 却下の保持（必須）

* `rejected` は削除せず保持すること。
* 書き出し時、負例として別途出力できること（学習に使うかは利用側の判断）。

## 6. 画面構成

| 画面 | 役割 |
|---|---|
| セッション一覧 | 記録済みセッションと進捗（レビュー済み/全体）を表示 |
| **選別画面** | 本仕様の中核。候補を順送りで選別する（F-I8-1/2/3） |
| タイムライン画面 | セッション全体を俯瞰し、見落とし補完と位置調整を行う（F-I8-5〜7） |
| 書き出し画面 | 窓長を指定して書き出す（F-I8-9） |

同期再生（F-I8-4）は**両画面が共有する単一の仕組み**として実装する。
選別画面は候補の前後数秒、タイムライン画面はセッション全体を対象とするが、
挙動は同一であり、対象範囲の違いだけで作り分けないこと。

既存の `VideoSyncPlayerView`（クリップ単位の動画・波形同期再生）を
この共通の仕組みへ発展させて再利用する。

> クリップ単位から連続タイムラインへの拡張は、単なる再生対象の差し替えではない。
> セッション全体が複数セグメントに分かれるため、シーク時に対象セグメントを解決し、
> 境界をまたぐ再生では再生対象を切り替える必要がある。この点は W6-T16c で扱う。

## 7. 既存機能との関係

| 既存 | 扱い |
|---|---|
| `ShotClass` | **そのまま使用** |
| `VideoSyncPlayerView` | 連続タイムラインへ拡張して再利用 |
| `ContentView.applyBulkTag` | 発想を踏襲。対象がスイングCSVからアノテーションへ変わる |
| `TrainingDataExporter` | 出力形式を踏襲。入力が「ラベル付きCSV」から「confirmed イベント＋連続記録」へ変わる |
| `SwingCSVParser.writeShotClass` | 連続記録では使用しない。既存データ用に残す |
| スイング一覧・詳細（現行） | 既存データの閲覧用として残す。新規セッションはアノテーション経由 |

## 8. 受け入れ基準

> 実装は完了しているが、下記はいずれも**実機・実データでの確認が未実施**。
> チェックは確認できた時点で入れる（2026-07-25）。

- [ ] 325件規模のセッションを **20分以内**に選別完了できる（1件あたり平均3.7秒）
- [ ] 承認＋球種指定が1操作で完了する
- [ ] 選別画面で候補へ移動すると、操作なしに動画と波形が同期再生される
- [ ] 選別画面・タイムライン画面のいずれでも、波形スクラブで動画が追従し、
      動画再生で波形が追従する（両画面で挙動が一致する）
- [ ] セグメント境界をまたいでシーク・再生でき、中断区間が時間軸上で判別できる
- [ ] 波形上でマーカーの無いピークを視認でき、その場でイベントを追加できる
- [ ] アプリを強制終了しても、それまでの選別結果が失われない
- [ ] 全ての操作が取り消し可能である
- [ ] 窓長を変更して再書き出しでき、再タグ付けが不要である
- [ ] 時刻オフセットの補正がセッション全体へ一括で反映される

## 9. 本仕様に含めないもの

* **自動分類**（球種の推論）— Phase 3 の学習済みモデル統合で扱う。
  本仕様は学習データを作る工程に限定する。
* 動画の編集・トリミング
* 複数人での分担タグ付け
* 既存のスイング単位データからアノテーションへの移行処理
  （保全データ328件はラベルが無く、移行する内容が存在しないため）
