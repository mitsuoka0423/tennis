# Requirements Specification: Tennis Swing Analyzer

## 1. プロジェクト概要 (Project Overview)

本プロジェクトは、Apple Watch Series 9（45mm）を利き腕に装着し、テニスにおけるスイング動作のセンサーデータを解析するスタンドアロン型watchOSアプリ、および解析用iOSアプリを開発する。
watchOS 10以降で利用可能な高頻度モーションAPI（`CMBatchedSensorManager`）を活用し、200Hz（実機検証済み）のサンプリングによる精密なスイング波形の取得と、オンデバイス（Core ML）でのショット分類を実現する。

---

## 2. 要求 (User Needs)

*2026-07-18 ヒアリングにて定義。要件・フェーズ構成の判断基準はすべて本節に遡る。*

### 2.1 解決したい課題

1. **自分のテニス上達**: フォームの質（スイング波形）とプレー内容（ショット分布・ポイント傾向）をデータで把握し、練習・試合の改善に活かしたい。
2. **技術的な楽しみ**: Watch の高頻度センサーや Core ML といった技術の活用自体が目的の一部である。特に Core ML モデルの構築を楽しみにしているため、「練習モードで学習データを収集 → 分類モデルを構築 → 試合モードで活用」という開発順序をとる。

※ 個人利用が前提。プロダクト化・他ユーザーへの配布は想定しない。

### 2.2 ユースケース1: 練習モード（優先）

> コートサイドに iPhone を三脚固定（将来はスロー動画撮影を兼ねる）。数球打ったら iPhone に歩み寄り、転送済みのスイング一覧から選んで波形を確認し、フォームを分析する。

* 1本打つごとにスイングが記録され、**打ってから約10秒以内**に iPhone で閲覧可能になること。
* スイング一覧は**時刻・連番**で見分けられること（将来はショット種別ラベルでも絞り込み）。
* Watch 側は**計測が生きていることがわかる簡易表示**で十分（間引きミニ波形・サンプルカウンタ等。波形を情報として読むのは iPhone の役割）。
* 将来: 同じ iPhone で撮影したスロー動画と波形を**上下並列で同期表示**し、外から見たフォームとセンサー波形を同時に確認したい（まず波形のみで開始）。

### 2.3 ユースケース2: 試合モード（Core ML 完成後）

> 試合中は Watch でスコアを記録しながらプレー。チェンジコートのタイミングでポイント単位の分析を確認する。

* **スコアのフル管理**: ポイント/ゲーム/セットを Watch で入力・管理できること。
* スイングデータがポイントに紐づき、以下を分析できること:
  * スコアの推移・現在スコア
  * ポイントごとのスイング数（ラリー長の傾向）
  * 勝ちポイントと負けポイントのスイング比較
  * どのスイングでポイントを落としたか（ストローク フォア/バック・ボレー フォア/バック・サーブ）
  * サーブの強さ・本数・確率（1st/2nd × ゲーム/セット/試合単位）
  * スイング種別の割合（ポイント/ゲーム/セット/試合単位）
* ショット種別を用いる分析は Core ML 分類（Phase 3）が前提。

## 3. アーキテクチャ設計方針 (Architectural Design Principles)

本プロジェクトでは、変更に強く、テスト容易性に優れたコードベースを維持するため、クリーンアーキテクチャ（Clean Architecture）をベースとした明確な関心の分離（Separation of Concerns）を適用する。

```
       ┌────────────────────────────────────────────────────────┐
       │                  Frameworks & Drivers                  │
       │  (Core Motion, HealthKit, WCSession, Core Data, UI)    │
       │                           ▼                            │
       │       ┌────────────────────────────────────────┐       │
       │       │    Interface Adapters (Presenters)     │       │
       │       │  (Gateways, ViewModels, Repositories)  │       │
       │       │                   ▼                    │       │
       │       │   ┌────────────────────────────────┐   │       │
       │       │   │     Use Cases (Interactors)    │   │       │
       │       │   │  (AnalyzeSwing, SyncDevices)   │   │       │
       │       │   │               ▼                │   │       │
       │       │   │      ┌──────────────────┐      │   │       │
       │       │   │      │ Entities (Domain)│      │   │       │
       │       │   │      │  (Swing, Motion) │      │   │       │
       │       │   │      └──────────────────┘      │   │       │
       │       │   └────────────────────────────────┘   │       │
       │       └────────────────────────────────────────┘       │
       └────────────────────────────────────────────────────────┘
```

### 3.1 依存方向ルール (Dependency Rule)

* **内側への単一依存**: 依存関係は常に外側（Frameworks/UI）から内側（Entities/Use Cases）へ向かう。コアなビジネスロジック（Entities/Use Cases）は、UIKit, SwiftUI, Core Motion, HealthKit などの Apple 特有のフレームワークに一切依存してはならない。
* **インターフェースによる境界分離 (Dependency Inversion)**: 外側のコンポーネント（例: センサー、データベース、通信部）は、対応する Use Cases 層が定義したプロトコル（インターフェース）を実装する形で接続する。

### 3.2 テスト容易性（Testability）の重視

* **Core Motion の抽象化**: センサーデータ取得部は `MotionSensorRepository` などのプロトコルで隠蔽する。これにより、テスト実行時にセンサーのダミーデータ（CSVから読み込んだ過去のスイングデータ等）を流し込むモック化を容易にし、実機を振ることなくユースケースおよび解析ロジックの単体テストを可能にする。
* **ロジックの分離**: SwiftUI の View や WatchKit のコントローラーは純粋に描画とユーザー入力のトリガーのみを担当し、スイング検知・ウィンドウ切り出し等のアルゴリズムはビジネスロジックとして完全に分離・独立してテスト可能とする。

## 4. システムコンポーネント構成 (System Components)

### 4.1 Apple Watch側 (watchOS App: Standalone)

* **装着**: 利き腕（右利きであれば右手首）に1台装着する。
* **動作モード**: スタンドアロンとしてセンサーデータを記録しつつ、スイング検知のたびに iPhone へ逐次転送する（iPhone 不達時はローカルに蓄積し、到達後に自動再送）。
* **バックグラウンド動作**: `HKWorkoutSession` を起動し、画面消灯時（スイング中）もプロセスサスペンドを防ぎ、センサーサンプリングを継続する。
* **データ永続化**: スイング単位の CSV ファイル（タイムスタンプはミリ秒精度）としてローカルに保存する。

### 4.2 iPhone側 (iOS App: Analyzer)

* **データ同期**: Watch からスイング単位の CSV ファイルを `WCSession` を介して受信する（練習中の逐次受信）。
* **可視化と分析**: スイング一覧・波形詳細・ショット種別の分布などを表示する。
* **データ保管**: 受信した全スイングデータを永続保存する（ML 学習データおよび長期の振り返りに使用）。

## 5. 機能要件 (Functional Requirements)

### 5.1 watchOS 側

* **[F-W1] ワークアウトセッション管理**
  * `HealthKit` を使用し、テニスのワークアウトセッションをアクティブ化・非アクティブ化できること。

* **[F-W2] 高頻度センサーデータキャプチャ**
  * `CMBatchedSensorManager` を用いて、加速度（3軸）および角速度（最大4,000度/秒、3軸）を取得すること。
  * サンプリングレートは **200Hz**（`deviceMotionUpdates()` の仕様上限）を採用する。
    * 実機検証（2026-07-17, Series 9）: 実測 200Hz・ロス率 0.2% を確認。
    * `deviceMotionUpdates()`（200Hz）は加速度・角速度が同期済み・重力除去済み。`accelerometerUpdates()`（800Hz）は加速度のみで、角速度とのペアリング処理が別途必要になるため採用しない（Phase 3 で分類精度が不足した場合に再検討）。
  * ロス率1%未満を維持すること。

* **[F-W3] スイング検知とウィンドウ切り出し**
  * 加速度ベクトルが閾値（デフォルト $3.0g$、調整可能）を超えた時点をインパクトとして検知すること。
  * インパクトの**前2秒・後2秒（計4秒・約800サンプル）**をスイングウィンドウとして切り出すこと。前後の秒数は**設定で調整可能**にすること。
  * 実装方式: リングバッファで常時直近データを保持し、検知時に前後を切り出す。ウィンドウが重なる連続スイングは適切に分割または結合すること。

* **[F-W4] ローカル永続化（スイング単位 CSV）**
  * **1スイング = 1 CSV ファイル**とすること。
  * レコードフォーマット: `[Timestamp (ms), AccX, AccY, AccZ, GyroX, GyroY, GyroZ, ShotClass]`
  * ファイル先頭にセッションID・スイング連番・検知時刻等のメタ情報を付与すること。
  * フォーマットは CSV に確定する（理由: Create ML / pandas への直結、デバッグ容易性、データ量が小さい。サイズが問題化した場合は転送前圧縮で対応し、バイナリ移行はその後に検討）。

* **[F-W5] スイング単位の逐次データ転送**
  * スイング検知・切り出しのたびに、`WCSession` の `transferFile` で iPhone へ自動送信すること（目安: 打ってから10秒以内に iPhone で閲覧可能）。
  * iPhone 不達時はローカルに蓄積し、到達後（またはワークアウト終了時）に未転送分を自動再送すること。

* **[F-W6] 計測中の簡易表示**
  * 計測が正常動作していることがわかるリアルタイム表示を行うこと（間引きミニ波形またはサンプルカウンタ・実測Hz・ロス率）。
  * 200Hz の生波形の常時描画は行わない（バッテリー目標を優先）。

* **[F-W7] ショット分類（Core ML）** *（Phase 3 Wave 2）*
  * 切り出したウィンドウを Core ML（Action Classification モデル）に流し、ショット種別（6分類: ストローク フォア/バック、ボレー フォア/バック、サーブ、その他）を判定すること。
  * 学習データは練習モードで収集し、アノテーション（手動タグ付け、F-I3）は iPhone 側で行う。
  * **学習データ収集・アノテーション方針**（2026-07-18 定義。詳細は docs/plans/PHASE3_PLAN.md）:
    * 1スイング = 1ラベル（ウィンドウ全体に同一クラスを付与）
    * 各クラス 50本で最初の学習実験、150本以上で実用精度を狙う目安とする
    * 精度目標の数値は、上記データが集まり実際に学習・評価してから確定する（データ無しでは検証不能なため）
  * Wave 2（データが目安に達してから着手）: Create ML Activity Classifier のスキーマ調査・学習・オンデバイス統合。

* **[F-W8] 試合モード: スコア管理** *（Phase 4）*
  * ポイント/ゲーム/セットのスコアを Watch で入力・管理できること（テニスのカウント規則に準拠）。
  * 各スイングデータに現在のポイントを紐づけて記録すること。

* **[F-W9] センサー値のリアルタイム時系列表示（デモ）**
  * **用途は「人に見せるデモ」**。腕の動きに即座に反応することを最優先とし、
    精密な読み取り（目盛り・数値の厳密さ）は二の次とする。
  * 加速度3軸・角速度3軸を、**軸ごとの値のまま**時系列の波形として表示すること。
    合成（ベクトルの大きさ）は行わない。
  * 加速度で1枚・角速度で1枚とし、各3軸を色分けして重ねること（X=赤・Y=緑・Z=シアン）。
  * 縦軸は固定スケールとし、既定は加速度 ±8g・角速度 ±1000°/s。
    実機で見ながら選べるよう、画面上で候補を切り替えられること。
  * 横軸は直近3秒、最新を右端とすること。
  * **計測（F-W1〜W6）とは独立した画面とすること。** 起動時にどちらを使うか選ぶ。
    計測中は計測画面から離脱できないこと（センサー取得の並走を避けるため）。
  * 保存・転送・ワークアウトセッションを伴わないこと。画面を開いている間だけ動作する。
  * 遅延を優先し、取得は `CMMotionManager`（50Hz・逐次配信）で行う。
    `CMBatchedSensorManager`（F-W2）は約1秒分をまとめて配信するためリアルタイム表示には使わない。

### 5.2 iOS 側

* **[F-I1] Watchデータ受信とハンドリング**
  * `WCSessionDelegate` を実装し、バックグラウンドでのファイル受信、ローカルストレージへの格納を行うこと。
  * 受信した全スイングデータを永続保存すること（削除はユーザー操作によるもののみ）。

* **[F-I2] スイング一覧と波形表示**
  * 受信済みスイングを**時刻・連番**の一覧で表示し、練習中に新着が自動で追加されること。
  * 一覧から選択したスイングの加速度・角速度波形を SwiftUI Charts で表示すること。
  * 将来: ショット種別ラベル（Phase 3 以降）による絞り込み。

* **[F-I3] アノテーション（手動タグ付け）** *（Phase 3）*
  * スイングに対しショット種別を手動でタグ付けできること（Core ML 学習データの作成を兼ねる）。

* **[F-I4] 解析エンジン** *（Phase 3〜）*
  * スイング位相の特徴点（インパクト時刻、スイング速度ピーク、減速開始点等）を検出し、スコアリングすること。
  * スコアリング基準（自己ベスト比較、理論値比較等）はPhase 3詳細設計時に定義する（TBD）。

* **[F-I5] 試合分析ダッシュボード** *（Phase 4）*
  * 要求 2.3 の分析項目（スコア推移、ポイント単位スイング数、勝敗ポイント比較、サーブ確率、種別割合等）を表示すること。
  * チェンジコートの短時間で確認できる画面構成とすること。

* **[F-I6] スロー動画と波形の同期表示** — ✅ 実装済み（2026-07-18 v2、Phase 5 を前倒し。詳細は docs/plans/PHASE5_VIDEO_SYNC_PLAN.md）
  * iPhone を三脚固定して撮影した動画と、対応するスイング波形を上下（動画→波形の順）で表示すること。
  * **録画は完全自動**（実機フィードバックにより v1 から刷新）: Watch の計測開始/終了に連動して
    iPhone のカメラ録画を自動的に開始/停止する（`WCSession.updateApplicationContext` で通知）。
    手動の録画ボタンは無い。
  * **データモデル**: 動画は**スイング単位のクリップ**として保存する
    （`Documents/videos/{sessionId}/{sequence}.mov`。CSV と対称的なレイアウト）。
    録画自体は練習セッション中連続的な中間データとして保持し、スイングの CSV が
    iPhone に届くたびに `AVAssetExportSession` でインパクト前後2秒を自動的に切り出す。
    中間データはセッション終了通知から60秒後（転送遅延の猶予）に削除する。
  * **「スロー」の実現方法**: 高フレームレート撮影は機種依存の検証リスクが高いため見送り、
    通常撮影 + `AVPlayer` の再生速度変更（0.25x/0.5x/1.0x）で実現する。
  * **操作性**: シークバーで再生位置を細かく指定できる。動画の再生位置は波形グラフの
    横軸（インパクトからの相対秒）と同期し、グラフ上に再生位置を示す縦線を表示する。
  * 前倒しの理由: 実データ収集を始めると CSV波形だけでは実際のショットが判別できず、
    アノテーション（F-I3）の精度が落ちるため。Phase 3 Wave 1 の実用化として先に着手した。
  * ⚠️ **2026-07-21 の実機検証で録画継続性の不具合が判明**（325スイング中クリップ1件）。
    データモデル（中間データの保持・削除）は F-I7 で刷新される。詳細は
    [docs/RECORDING_RELIABILITY_SPEC.md](RECORDING_RELIABILITY_SPEC.md)。

* **[F-I7] 録画の継続性と観測性** — ✅ 実装済み・実機未検証（2026-07-25。詳細は docs/RECORDING_RELIABILITY_SPEC.md）
  * 練習セッション中、**iPhone を操作しなくても録画が継続すること**。録画中は画面の自動ロックを抑止する。
  * iOS による録画中断（着信・バックグラウンド遷移等）から**自動的に復帰すること**。
    カメラ撮影を継続できるバックグラウンドモードは iOS に無いため、
    中断を防ぐのではなく検知して復帰する設計とする。
  * 録画は**セグメント分割**して保持する（`Documents/video_sources/{sessionId}/{index}.mov` + `manifest.json`）。
    中断復帰時に新セグメントを開始し、1セグメントの最大長を10分とする。
  * セグメントは**既定で保持し自動削除しない**（2026-07-25 改訂。当初は「クリップ化まで保持・上限7日」）。
    データ収集方針の変更によりセグメントが一次データになったため。削除はユーザー操作に限る。
  * セッションごとに**診断記録**（セグメント・中断回数・クリップ成功/失敗・録画カバー率）を
    保存し、App内で閲覧・共有できること。
  * ログは `os.Logger` を使用し、実機を Mac に接続していなくても事後に追跡できること。
  * 経緯: 2026-07-21 の実機検証で、スイング検出・転送は正常（325件・200Hz・時計ずれ0.2秒）
    だったにもかかわらずクリップが1件しか生成されなかった。原因は
    `willResignActive` での録画停止に対する再開経路の欠如。過去11セッション全てで
    同じ症状が出ており恒常的な不具合だったが、短時間の動作確認では顕在化していなかった。

* **[F-I8] 連続記録と事後アノテーション** — ✅ 実装済み・実機未検証（2026-07-25。詳細は [docs/ANNOTATION_SPEC.md](ANNOTATION_SPEC.md)）
  * データ収集を「検知して切り出す」から**「全区間を記録し練習後にタグ付けする」**へ移行する。
    検知器は廃止せず、オフラインで候補を提示する役割へ変更する（門番から提案者へ）。
  * センサーを**全区間保存**すること（約46MB/時）。動画は既に連続録画されている。
  * 練習後に動画とセンサー波形を見ながら、候補の**選別と球種の付与**を行えること。
    1件あたり5秒以下、325件規模で20分以内を設計目標とする。
  * タイムライン上で**波形と動画を双方向に同期**させ、セッション全体を1本の連続した
    時間軸として再生・シークできること。複数セグメントをまたぐ場合も連続して扱い、
    中断区間は動画の欠落として明示すること。
  * 検知器の見落としを波形上で発見し、同期再生で確認しながら手動で補完できること。
  * 「スイングではない」と却下した候補は**削除せず負例として保持**すること。
  * 学習データの**窓長は書き出し時に指定**できること。再収集・再タグ付けなしに変更可能とする。
  * 経緯: F-I7 の調査過程で、re-arm により 3g超イベントの42%が未発行（10g超の打球4件を含む）、
    閾値変更のたびに実練習1時間の再収集が必要、ラベルが全件空欄で精度を測る土台が無い、
    という3点が判明した。いずれも「撮影時に捨てたものは戻せない」ことに起因する。

## 6. 非機能要件 & 技術的制約 (Non-Functional Requirements & Constraints)

* **対応プラットフォーム (Deployment Target)**:
  * watchOS 10.0以上 (Series 9, 45mm ターゲット)
  * iOS 17.0以上

* **サンプリングレート**:
  * ターゲット: 200Hz（`deviceMotionUpdates()` の仕様上限。実機検証 2026-07-17 で実測 200Hz・ロス率 0.2% を確認）
  * ロス率: 1% 未満を維持すること

* **転送レイテンシ**:
  * 練習モードにおいて、スイングから iPhone での閲覧可能まで**10秒以内**を目安とする（iPhone がコートサイドの Bluetooth 到達圏内にある前提）。

* **バッテリー消費量**:
  * 1時間の連続計測において、Watch単体でのバッテリー消費率を 20% 以下に抑えることを目標とする。
  * 1次フィルタによる不要な処理の抑制を主な手段とし、実機での消費量を実測して目標値の妥当性を検証すること。

* **ストレージ**:
  * Watch側: ファイル転送完了後にローカルの一時キャッシュデータを自動削除するクリーンアップ機構を設けること。
  * iPhone側: 全スイングデータを永続保存する（1スイング約60KB・年間でも数百MB程度と小さいため、容量上限は設けない）。
  * iPhone側: 録画の中間データは大きい（1080p で 1時間あたり 4〜6GB）。ただし
    **自動削除も期限削除も行わない**（2026-07-25 改訂。当初は「クリップ生成完了後に削除・上限7日」）。
    連続記録が学習データの素材となったため、期限で消すと素材ごと失うことになる（F-I7-4）。
    削除はユーザー操作に限り、空き容量の逼迫は録画画面で警告する（F-I7 T17）。
  * iPhone側: センサーの連続記録は約46MB/時（200Hz・CSV）。5分ごとのチャンクに分けて転送する（F-I8）。

* **録画カバー率**（F-I7）:
  * 練習セッションの経過時間に対する実録画時間の比を 95% 以上とする。
  * 検出スイング数に対するクリップ生成成功率を 95% 以上とする。
  * 2026-07-21 実測: カバー率 1% 未満・クリップ生成率 0.3%（325件中1件）。是正対象。

* **観測性**（F-I7）:
  * 実機を Mac に接続していない状態でも、録画の開始/中断/復帰/停止とクリップ生成の
    成否を事後に追跡できること（`os.Logger` + セッション診断記録）。
  * 理由: 実機検証は1時間の実練習を要し再現コストが高い。1回の検証から最大限の情報を得る。
